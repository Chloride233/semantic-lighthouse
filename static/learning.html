学习主线

先学产品判断，再学代码细节

面试时最重要的不是逐行复述，而是能把每个模块放回同一条风险控制链路里。

01

定位

不是通用 RAG，也不是自由 Agent，而是 Ontology semantic operating layer workspace。
02

证据

RAG 不是终点，它提供 citation、confidence、knowledge gaps 和可保存证据。
03

建模

自动化只生成 proposal，人类审核决定哪些 draft 进入 package。
04

合同

business contract 是应用可读的稳定语义边界，不等于数据库 schema。
05

运行

runtime query 证明 Ontology 能读真实数据，并保留 provenance 和 audit。
06

演进

Phase 19 用 data pack、mapping contract 和 rule validation 推进真实数据闭环。
架构图

先看懂系统怎么流动

这几张图不追求节点多，而是追求你能按顺序讲出来：谁发起、经过哪层、谁决定、哪里留下审计证据。

1. 系统分层架构图

读图顺序：从左到右看调用链，从上到下看分层。重点看所有读写都被 FastAPI 和 Service Layer 收束。

一句话：前端不直接碰数据，Agent 也不直接碰数据，核心能力都收束到服务层。

2. Ontology Pipeline 架构图

读图顺序：上面是治理平面，下面是运行平面。accepted package 是两个平面的分界点。

一句话：Ontology 不是自动生成后直接上线，而是 proposal → review → package → runtime。

3. 权限与审计边界架构图

读图顺序：左边是身份，中央是服务端授权边界，右边是允许访问的数据域和审计域。

一句话：权限不是 UI 标签，而是服务端查询、写入和审计共同保证的执行边界。

4. RAG 到 Ontology 的证据架构图

读图顺序：RAG 只产生答案和证据候选；只有用户保存，证据才进入项目；只有人审，证据才影响模型。

一句话：RAG 负责提供证据，不负责自动改模型；人类保存和审核才让证据进入 Ontology。

术语表

这些英文词在本项目里是什么意思

不要按字典硬翻。下面解释的是它们在 Semantic Lighthouse 架构里的具体角色。

API BoundaryAPI 边界

所有外部请求进入系统的门。权限、参数校验、路由分发都先在这里发生。

Service Layer服务层

真正执行业务规则的地方。比如生成草稿、构建模型包、运行查询、写审计。

Persistence持久化层

长期保存数据的地方，包括 PostgreSQL、pgvector 和文件存储。

Runtime运行时

模型不只是写在文档里，而是真的能被查询和使用的执行阶段。

Governance Plane治理平面

人审、质量门、建模草稿、模型包这些“决定语义是否可信”的流程。

Runtime Plane运行平面

已经审核过的语义模型被拿来查询数据、生成审计和交付物的流程。

Evidence证据

支撑一个判断或建模决定的来源，例如文档、RAG 回答、数据 profile。

Draft草稿 / 候选

系统或用户提出的建模建议。它不是最终模型，必须经过人工审核。

Package模型包

审核通过后的不可变语义快照。后续查询和交付物都能追溯到它。

Business Contract业务合同

应用可读取的业务语义接口，描述对象、属性、关系、动作和 semantic_hash。

Binding绑定

把业务属性连接到真实数据列，例如 `equipment.status -> CSV 的 status 列`。

Typed Query类型化查询

按业务合同校验字段和类型后再查询，不让前端或 Agent 直接写 SQL。

Audit审计

记录谁在什么时候做了什么。失败也要记录，否则系统会只留下成功假象。

Provenance来源 / 溯源

说明结果来自哪个模型包、哪个数据集、哪个 hash，但不暴露 raw data 或路径。

Artifact交付物

最终给人看的结果文件，例如 markdown 报告，用来支持面试或项目复盘。

踩坑经历

这些坑是面试里的高价值故事

每个案例都包含问题、工程判断、修复方式和验证数据。它们比“我用了某某框架”更能体现工程成熟度。

Audit claim drift

测试通过不等于能力存在

Phase 14.5 文档声称 query audit 已实现，但代码里没有 audit model、migration、写入路径和读取验证。后续补上 `OntologyRuntimeAudit`、migration `0023`、服务写入和真实 DB 断言。

优化数据：最终形成 94 个 runtime tests，254 个 Phase 14 combined tests，749 个 full non-E2E tests。

Project scope

上下文标签不是执行隔离

给 Conversation、Task、AgentRun 加 `project_id` 后，如果检索仍读全 group，就会产生虚假的项目隔离感。修复后，项目 scoped retrieval 只读 active ProjectEvidenceLink documents。

优化数据：S2.3B 通过 16 focused tests、100 related tests，并覆盖 832 collected non-E2E tests。

PostgreSQL gap

SQLite 测试覆盖不了 pgvector SQL

SQLite fallback 全绿，但真实 PostgreSQL/pgvector 曾暴露向量 SQL 绑定和类型问题。项目因此保留 fast local tests + PostgreSQL smoke gate 的双层验证。

优化数据：Phase 18 验证 28/28 migrations on PostgreSQL + pgvector，HTTP API smoke 9/9 PASS。

Human review

自动化只能提案，不能替人决定

Phase 11 把生成结果限制为 proposed drafts。accepted/rejected 必须由 owner/admin 做一次性审核，re-review 返回 409，batch review 原子化。

优化数据：Phase 11.4 增加 33 tests，验证权限、状态不可逆、批量原子性和 rejected-note 要求。

Retry safety

重试不能破坏已可用文档

早期手动 retry 会把 ready document 置回 uploaded，若 ETL 失败会让原本可检索的文档失效。修复后 ready 文档失败回滚保持可用。

优化方法：新版本成功后再替换旧 chunks，失败时保留旧版本作为服务 fallback。

UI polish

视觉优化必须有可验证边界

F2C 不是随意美化，而是解决 checkbox 尺寸继承、表格滚动、移动端 overflow、dialog focus trap 和 keyboard nav 等具体问题。

优化数据：E2E 扩展到 18 tests，verify_ui 保持 47/47，后续视觉基线刷新达到 53/53。

架构与技术选型

项目的价值来自克制，而不是堆框架

这些取舍能帮助你回答“为什么不用 X”这一类面试问题。

继续保留

FastAPI、SQLAlchemy、Alembic、PostgreSQL/pgvector、Pydantic、原生前端、fake provider smoke、受控 Agent registry。

理由：可解释、可测试、可审计，适合求职项目展示工程边界。

暂缓引入

Neo4j、rdflib/OWL/HermiT、LangGraph、MCP runtime、OSDK/codegen、自动 Action execution/writeback。

理由：当前收益不如 mapping contract、rule validation 和 runtime 边界拆分。

Phase 19 推荐表达：Real Data Semantic Mapping + Rule Validation Loop。让系统证明字段含义可解释、业务规则可验证、异常能进入治理反馈，而不是马上追求 OWL 或图数据库完整感。

面试训练

准备能体现判断力的问题

每个答案都要落回业务、技术、风险和验证四个维度。

为什么不是普通 RAG？

普通 RAG 是 question → retrieve → answer。这个项目把 answer 保存为 evidence，再进入 modeling draft、package、runtime query 和 outcome artifact，每一步都有权限、审计和人审边界。

为什么不用 LangGraph？

当前 Agent FSM 已经覆盖工具白名单、risky confirmation、audit replay。没有测得 FSM 不够用之前，引入 LangGraph 会降低可解释性和作品集可控性。

为什么不让 Agent 自动写 Ontology？

Ontology 是企业语义合同。自动写入会把噪声、误判和幻觉变成治理事实。当前设计让自动化提案，人类审核决定，审计保留责任链。

business contract 和数据库 schema 有什么区别？

数据库 schema 描述表结构；business contract 描述业务对象、属性、关系、动作、权限要求和语义 hash，是应用和未来 Agent 能安全消费的语义边界。

为什么 package 要 immutable？

因为 runtime query、audit、outcome artifact 都要能追溯到同一个语义版本。可变 package 会破坏“当时基于什么模型做的决策”这一审计问题。

Phase 19 最值得做什么？

不是换栈，而是 real data semantic mapping + rule validation：让字段映射、业务规则、异常反馈和下一版建模形成闭环。
