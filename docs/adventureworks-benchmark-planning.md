# AdventureWorks External Benchmark — Planning

**Date**: 2026-06-22
**Status**: Planning only — no implementation, no data download.
**Phase reference**: Phase 19 closeout follow-up candidate.

## Summary

Microsoft AdventureWorks is a well-known OLTP sample database for SQL Server
that models a bicycle manufacturing company. It contains production,
purchasing, sales, HR, and person schemas (~70 tables total). The
manufacturing/supply-chain subset makes it an excellent external benchmark
for Semantic Lighthouse ontology operationalization.

**This document evaluates feasibility. It does not recommend downloading,
wiring, or implementing anything at this stage.**

## Why AdventureWorks

| Factor | Assessment |
|--------|-----------|
| Domain match | Bicycle manufacturing — BOM, work orders, routing, inventory, vendors |
| Schema richness | ~70 tables, well-documented PK/FK, realistic cardinalities |
| Availability | Public domain, downloadable from Microsoft/sql-server-samples GitHub |
| Licensing | MIT License — safe for evaluation and benchmarking |
| Industry recognition | Widely used in SQL Server training, BI demos, and data engineering |
| Contrast with current | Real-world schema complexity vs our 13-table synthetic generator |

## Schema Alignment with Phase 19 Pipeline

The existing P19 pipeline expects:
- 13 CSV files with `table_name.csv` naming
- `manifest.json` with PK/FK declarations
- `mapping_contract.json` with column-to-property mappings

AdventureWorks data would need:
1. **Extraction**: SQL query or export to CSV (one file per table)
2. **Manifest generation**: Produce `manifest.json` matching P19 contract spec
3. **Mapping contract**: Map AW column names to Ontology business properties
4. **Rule validation**: Run existing `validate_business_rules.py` against AW data
5. **Governance feedback**: Generate governance candidates from AW findings

The P19 pipeline code (`generate_manufacturing_dataset.py`,
`generate_mapping_contract.py`, `validate_business_rules.py`,
`generate_governance_feedback.py`) is designed to be data-source agnostic —
it reads manifest + CSV, not a specific generator. An AW adapter would only
need to produce correctly-formatted manifest.json and CSV files.

## Integration Approach (Recommended)

### Option A: Standalone AW data pack (recommended)

```
data/adventureworks/
  manifest.json          # Generated from AW schema
  Product.csv            # Direct export
  WorkOrder.csv
  ...
  mapping_contract.json  # Generated by existing script
  rule_validation_report.json
  governance_feedback.json
```

**Pros**: Reuses 100% of existing P19 pipeline code. No generator modification.
**Cons**: Requires one-time extraction script (~50 lines of SQL/CSV export).

### Option B: AW-aware generator

Build a new `generate_adventureworks_dataset.py` that downloads and extracts
AW data programmatically.

**Pros**: Reproducible from source.
**Cons**: Network dependency, larger scope, mixes real data ingestion with
synthetic generation concerns.

### Recommendation: Option A

Start with Option A. The extraction is a one-time mechanical step. The value
is in running the existing P19 pipeline against a real-world schema and
observing what the rules find.

## Risks

| Risk | Severity | Mitigation |
|------|----------|-----------|
| CSV export fidelity | Medium | AW uses SQL Server types (money, datetime2, hierarchyid). Export to CSV may lose precision or hierarchy metadata. Validate with checksums. |
| Scale difference | Low | AW WorkOrder has 72K rows vs our 10-row tiny preset. P19 scripts are stdlib-only CSV readers — they scale linearly. Test with medium preset first. |
| Schema mismatch | Medium | AW has composite keys, multi-column FKs, and nullable patterns our current manifest supports but hasn't been tested against. May need minor manifest schema extension. |
| Licensing | Low | MIT License. Document license in extracted data pack. |
| Time investment | Medium | Even with planning, extraction + manifest + mapping + validation + test is a full Standard Lane slice. Budget cautiously. |

## What We Learn (Value Proposition)

Running the P19 pipeline against AdventureWorks proves:

1. **Schema generality**: The manifest/mapping_contract/rule_validation
   pipeline works with real external data, not just our synthetic generator.
2. **Scale readiness**: 72K-row WorkOrder table validates that stdlib CSV
   readers handle realistic OLTP volumes.
3. **Rule signal quality**: How many governance candidates does the pipeline
   produce for curated (non-synthetic) data? A low count validates rule
   precision; a high count reveals gaps.
4. **Mapping contract extensibility**: Can the controlled vocabularies and
   semantic roles we designed for 13 synthetic tables generalize to a
   different schema?
